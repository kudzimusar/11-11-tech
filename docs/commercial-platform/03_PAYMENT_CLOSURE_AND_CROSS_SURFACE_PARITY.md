# Commercial Platform 1.1 — Payment Closure & Cross-Surface Parity

**Status:** Canonical amendment for Mobile 1.1 / desktop UAT  
**Governing parent:** `00_MASTER_PLAN_AND_OPERATIONS.md`  
**Use with:** `01_DEPLOYMENT_AND_ACTIVATION_RUNBOOK.md`, `02_ADMIN_AND_CLIENT_MANUAL.md`, `docs/NATIVE_MOBILE_APP.md`

This amendment does not replace the Commercial Platform master plan. It closes the gaps found during implementation review and defines the authoritative behaviour that web/desktop and native mobile must share before UAT. If an older implementation note conflicts with this file, this amendment governs the 1.1 parity lane while preserving every invariant in the master plan.

## 1. Cross-surface operating model

11-11 Tech has one commercial system of record, not separate web and mobile businesses.

```text
Public web / Native app
        |
        +--> Start a Project --> shared hardened lead intake
        |
        +--> Pay an invoice / Client workspace
                |
                +--> Supabase Auth
                +--> tenant-scoped commercial tables + narrow RPCs
                +--> private document vault
                +--> Stripe Checkout / webhook reconciliation
                +--> same invoice, payment, acceptance and audit ledger
```

The native app may use native navigation, SecureStore, safe-area composition and device interactions, while the browser uses its own UI primitives. The business state and server rules must remain identical.

The **Company Admin command centre remains a desktop/large-screen operational surface** because dense client/project/document/billing administration is materially more usable there. Native Mobile exposes an explicit Company Admin link, but does not fork or duplicate admin business logic.

## 2. Exact invoice settlement

A supplied invoice reference is never treated as a generic project payment request.

1. The anonymous Pay Invoice entry captures only invoice/project reference + billing email.
2. Financial data remains hidden until authenticated client membership is established.
3. If the reference resolves to an invoice, the client UI shows that exact invoice, including status, total, amount already paid and remaining amount.
4. Agreement requirements remain enforced before payment.
5. Checkout is created with `invoiceId`, not merely `paymentPlanId`.
6. The server accepts only `open` or `partially_paid` invoices and derives the exact remaining amount itself.
7. Paid, void, uncollectible or otherwise non-payable invoices cannot create Checkout.
8. Web and native use the same `stripe-checkout` endpoint and same invoice ledger.

## 3. Additional/partial project payments

A client may make an approved additional payment only when the selected finite plan allows it.

Server rules are authoritative:

- recurring subscriptions do not use project-balance extra payments;
- the configured minimum extra amount is enforced;
- the remaining payment-plan obligation is calculated server-side;
- the remaining project receivable is calculated from confirmed payments;
- a requested amount above the payable outstanding balance is rejected rather than silently accepted or capped;
- the browser/native client never decides the authoritative receivable.

This closes the overpayment condition that existed when an extra payment was capped only against the original plan total.

## 4. Manual/offline payment custody

Approved external methods remain `bank_transfer`, `cash`, `mobile_money`, `paypal`, or `other`.

Before a staff member records money, the admin function validates that the invoice/installment belongs to the selected project and derives the remaining target balance. A manual payment above the invoice, installment or project outstanding balance is rejected.

After a successful ledger write:

- invoice/installment status is reconciled;
- the payment plan is completed when no obligation remains;
- the project may activate according to the normal lifecycle rule;
- a receipt reference is generated by the database;
- a branded receipt document is created through the same `document-render` service and stored in the private `client-documents` vault;
- an audit event records the amount, method and receipt-render result;
- the billing contact receives a payment-recorded email when email delivery is configured.

External money is never erased if PDF rendering fails. A render failure is observable and must be remediated, while the financial ledger remains truthful.

## 5. Scheduled-charge payment method binding

Explicit authorization applies to a specific payment plan and, after the first interactive Stripe Checkout, to the payment method actually used for that authorised flow.

`payment_authorizations` therefore stores:

- `stripe_payment_method_id`;
- `payment_method_saved_at`.

The Stripe webhook retrieves the successful PaymentIntent, records its PaymentMethod on the still-active authorization and may mirror it to the Stripe Customer default for normal Stripe behaviour.

The finite-installment billing runner **must use the PaymentMethod stored on that authorization**. It must not list attached cards and select the first one. If the authorization exists but no authorised payment method is stored, no off-session charge is attempted; an audit event and client action-required email are produced instead.

Recurring subscriptions remain managed by Stripe Subscription billing after interactive authorization.

## 6. Lead-to-organisation identity

A new lead should not create duplicate commercial shells for the same commercial identity, while a shared billing inbox must not collapse unrelated legal entities.

Provisioning uses:

`normalised billing email + normalised organisation/trading identity`

The trigger takes a transaction advisory lock for that identity before lookup/create. A matching organisation is reused; a different organisation name sharing the same billing email remains a separate organisation.

The company-admin project-creation path follows the same identity rule.

## 7. Native client custody

Native Mobile 1.1 adds first-class routes for:

- **Pay an invoice**;
- **Client workspace**.

The app uses the same Supabase and commercial Edge Function contracts as web. It does not embed service-role, Stripe secret, webhook, Resend or document-render credentials.

### Authentication

Public configuration:

- `EXPO_PUBLIC_SUPABASE_URL`
- `EXPO_PUBLIC_SUPABASE_ANON_KEY`
- `EXPO_PUBLIC_COMMERCIAL_API_URL`

The auth redirect is created with Expo Linking and returns to `/client`. Production must allow the app deep link `eleveneleven://client` in Supabase Auth redirect configuration. Development/Expo Go redirect URLs used during UAT must also be explicitly allow-listed.

Access/refresh tokens are stored with Expo SecureStore, not AsyncStorage or source code. Expiring access tokens are refreshed through the Supabase Auth public refresh endpoint.

### Documents

The private Storage bucket stays private. Native clients request a short-lived signed URL from `commercial-document-link`, which validates the authenticated user and active organisation membership before signing the exact issued document path for five minutes.

### Agreements and payments

Native mirrors the web states:

- project overview;
- paid/outstanding totals;
- document vault;
- invoices and receipts;
- payment-plan selection;
- exact invoice resolution;
- open-before-accept document acknowledgement;
- explicit scheduled/recurring authorization;
- Stripe-hosted Checkout.

The server remains authoritative for every amount and permission.

## 8. Stripe return path

Stripe success/cancel currently returns to the hosted 11-11 Tech result page. That page includes both the web client workspace and an `eleveneleven://client?...` return link. When the native app returns to the foreground it refreshes the shared ledger; it does not infer payment success from the browser redirect.

The webhook remains the authority for payment confirmation.

## 9. UAT certification matrix

Before merge/live activation, use one controlled test client and test project on **both desktop web and iPhone 17**.

### Journey A — project onboarding

Lead → prospect organisation/project shell → admin review → commercial package → client invitation → secure login.

### Journey B — exact invoice

Pay Invoice → reference/email → auth → exact invoice → required docs → Stripe test Checkout → webhook → invoice paid/partially paid → receipt PDF → updated client balance.

### Journey C — finite instalments

Select plan → agreement → explicit scheduled-charge authorization → first interactive payment → PaymentMethod bound to authorization → later billing run uses that exact method.

### Journey D — additional payment

Allowed extra payment above minimum succeeds; below minimum and above outstanding are both rejected server-side.

### Journey E — manual payment

Admin records approved offline payment → target balance cannot overpay → ledger updates → branded receipt generated → client sees receipt/balance on web and native.

### Journey F — document custody

Required issued PDF opens before acknowledgement; accepted version/hash remains immutable; native signed link expires; another organisation cannot access it.

### Journey G — lifecycle/recovery

Background/reopen native app, refresh sessions, failed/cancelled Checkout, webhook retry/idempotency, payment failure, sign-out/sign-in, multiple projects, paid invoice re-entry.

## 10. Activation gates that remain external

Code completion does not equal live-money authorization.

Before real clients pay:

1. Connect the correct **11-11 Tech Supabase project**.
2. Apply all commercial/native migrations in order, including `20260913155000_commercial_payment_closure.sql`.
3. Deploy `commercial-admin`, `document-render`, `commercial-document-link`, `stripe-checkout`, `stripe-webhook`, `commercial-billing-run`, and the hardened `lead-intake` function.
4. Configure server-only secrets from the deployment runbook.
5. Add web and native redirect URLs to Supabase Auth.
6. Connect the correct **11-11 Tech Stripe account in test mode**.
7. Configure the webhook and scheduled billing invocation.
8. Bootstrap the intended company admin.
9. Complete Journeys A–G in test mode on desktop and native.
10. Obtain final legal approval for production contract wording.
11. Only then perform the documented live cutover.

The unrelated `church-os-dev` Supabase project and Tengasell Stripe account are explicitly out of scope and must not be mutated for this system.
